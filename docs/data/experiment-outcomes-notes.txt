Reasons for choosing certain metric numbers:


http-rate-limit: 
The default correctionMultiplier of 0.1 seemed to strike a good balance between smoothing and not being too slow when I did some simulations with a Python script and tried it out with some queries that federate with Wikidata.
But since WIkidata has a 'time budget' limit for queries, a rate limiter like that will not fix it, because it does not keep track of the 'budget' used.
You could try reducing the failure multiplier to 1.0 and leaving the correction multiplier to 0.1 or 0.05. That way, the smoothing (low correction multiplier) would still be there, but a failed request would not make the request interval jump up (which was needed for endpoints with strict rate limits).




VoID / COUNT / ASK:
Three different approaches to gathering metadata for query planning and execution were tested. The default method used by Comunica is sending COUNT queries to sources.


By modifying the ’useAskIfSupported’ option of prune-empty-source-operations within the actor-optimize-query-operation actor, ASK queries were used instead of COUNT queries.


By utilizing the actor-rdf-metadata-extract-void actor, Comunica will first use VoID descriptions from sources (if available) then defaults to COUNT queries if the VoID cannot be found or does not offer useful estimations. 


We chose not to also test the use of ASK queries with VoID because during testing (using query RHEA 13 w/o SERVICE clause) the number of HTTP requests during the query planning phase and execution phase were the same between COUNT + VoID and ASK + VoID setups.

Interesting findings:


Error With SERVICE, functional without SERVICE:
A curious case where a query (Rhea 13) throws a “QueryEvaluationException” error when executed WITH a SERVICE clause, but executes properly and returns results when executed using Comunica with the SERVICE clause removed.


Strange SERVICE behavior from some endpoints:
When sending a query containing a SERVICE call to a Virtuoso endpoint, Virtuoso rewrites the query within the SERVICE clause before sending it to the source designated in the SERVICE clause. This becomes problematic in some instances. One particular case is when VALUES are included within the SERVICE clause. In this case, Virtuoso rewrites the triple patterns within the SERVICE clause to be FILTERs containing each value to be passed into the SERVICE clause.  


Example:
Original Query:
SELECT * WHERE {
  SERVICE <http://rdflib-endpoint/> {
      SELECT ?o WHERE {
        VALUES ?s { <http://subject1> <http://subject2> }
        ?s ?p ?o .
      }
    }
}


Virtuoso “re-formed” query (received by SERVICE source):
SELECT  ?o
 WHERE {  ?s ?p ?o .
     FILTER (isIRI (?s ))
    FILTER (  (( ?s = <http://subject1>) || ( ?s = <http://subject2>)) ) }






SPARQL Endpoint crashes mid-experiment:
When executing a test of the benchmark on 07/04/2025, one of the SPARQL endpoints included in many of the queries (https://biosoda.unil.ch/emi/sparql) crashed and caused many of the tests to fail. The crashing of this endpoint occurs after the very first query I submit in my workflow. Specifically, during this first query (001), Comunica submits 1282 HTTP requests (897 of which are to the biosoda endpoint). Following these requests during the first query (which does not produce results and instead throws a timeout-related error), the biosoda endpoint throws the error: `Virtuoso 42000 Error SR452: Error in accessing temp file` for all further requests until the endpoint is rebooted by a maintainer.
 
According to Tarcisio this seems to be a Virtuoso hardware bug that has been noticed in the past. The error is related to Virtuoso attempting a large number of processes in parallel. Due to this large parallel processing, the Virtuoso server is either A) running out of memory in the temp file referenced OR B) there is a bug in the implementation that limits the number of processes running in parallel that can access the temp file simultaneously. To address potential issue A, Tarcisio increased the maximum size of the temp file to 60GB of disc space from the previous 1GB. [Testing needs to be done to determine if this will fix the observed issue] 


VoID description usage runs into errors when query contains inner filter
Example is seen in the case of query 017 with the triple pattern FILTER (UCASE(?geneLabel) = UCASE('ins')). The resulting query plan likely (need to check to be sure) contains inaccurate cardinality estimates and therefore the execution of this query is unsuccessful due to a very large number of HTTP requests sent during the execution phase. 




General Problem – Count queries for source selection on large endpoints
A general issue with using Comunica for query planning and source selection is that, but default, Comunica send a large number of (sometimes computationally complex) COUNT queries that commonly result in timeout errors (both client and server side) and high computational costs on the SPARQL endpoints specified as sources. As a result of these COUNT queries, there are also a large number of HTTP requests sent during the query planning and execution phases.
